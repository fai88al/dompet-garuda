# Bayar QR Offline — QR Payload Spec (FR23)

> For the firmware team. This is a data-format spec, not a backend API — there is no new
> backend endpoint for Bayar QR Offline. See CLAUDE.md §14.3 and PRD FR23/R11 for the
> product context.

## What this is

Bayar QR Offline is **not a new payment flow**. It is the existing offline BLE Transfer
flow (device-to-device, Ed25519-signed, no internet), where the receiver's device displays
a QR code as a faster way to hand the payer's device the receiver ID and amount, instead of
the payer typing them in manually. Everything after the scan — mutual authentication,
transaction signing, counter increment — is identical to a manually-initiated offline
Transfer.

## Payload format

```
{receiverDeviceId}|{amount}|{nonce}|{expiresAt}
```

Pipe-delimited, four fields, in this exact order.

| Field | Type | Constraints |
|---|---|---|
| `receiverDeviceId` | UUID | The receiving device's registered `device_id`. |
| `amount` | positive integer | Whole Rupiah (no decimals — money is `BIGINT` everywhere in this system, see CLAUDE.md §7.3). |
| `nonce` | random string | Generated by the **receiver's** device for local display-side deduplication only (e.g. so the receiver's screen can tell two consecutive QR displays apart). **This is not the same thing as the server-side nonce used by Bayar QR Online (`payment_requests.nonce`)** — there is no server round-trip here, so nothing checks this value for uniqueness or replay. It exists purely as a local UX aid. |
| `expiresAt` | ISO-8601 timestamp (UTC) | Used only by the **device** to decide whether it should still show/honor this QR on screen. The server never sees or checks this value — offline trust comes entirely from the BLE signing exchange that follows the scan, not from this timestamp. |

Keep the payload small — QR codes have limited capacity, and this one must be scannable at
typical camera resolutions on constrained hardware (small device screens, modest camera
sensors).

## Recommended QR parameters

- **Error correction level: M** (not H). Level M gives enough tolerance for typical
  phone/device-camera scanning conditions (minor smudging, imperfect angle, ambient glare)
  without producing an unnecessarily dense code on a small device screen. Level H roughly
  doubles the redundant data encoded, which only makes sense when the code must survive
  physical damage (e.g. a printed sticker) — not the case here, since this is a
  freshly-rendered on-screen code.
- **Estimated QR version: 3–5.** A payload like
  `a1b2c3d4-e5f6-7890-abcd-ef1234567890|500000|Kj8mZpQ2Nx|2026-08-19T10:15:00Z` is
  roughly 65–75 alphanumeric characters. At error correction level M, that comfortably fits
  within QR version 3 (~53 alphanumeric chars) to version 5 (~106 alphanumeric chars) —
  version 4–5 gives headroom for longer nonces without needing to renegotiate the format.

## What happens after the scan

After scanning, the payer's device initiates the **same BLE mutual-authentication and
signing flow as a manually-initiated Transfer** (CLAUDE.md §4 device auth model,
§3 "offline sync flow"). The QR payload is consumed once, locally, purely to pre-fill the
transfer amount and receiver on the payer's device — **it is never sent to the backend
directly**. The backend only ever sees the resulting signed offline transaction at the next
sync, same as any BLE transfer.

## The `origin` field (backend, optional)

Separately, the signed batch a device uploads at sync time (`POST /device/sync`, see
`SyncBatchRequest`/`SyncOfflineTxnRequest`) MAY include an optional `origin` field per
transaction, set to `"QR"` when that specific transaction was initiated via a QR scan as
described above (or omitted / set to `"BLE"` for a manually-entered transfer — `"BLE"` is
the default when the field is absent).

This field is **purely for backend observability** — it lets the backend team see what
fraction of offline transfers originate from QR scans vs. manual entry. It has **no bearing
on trust or verification**: the settlement service applies the exact same signature
verification, counter/replay checks, and pouch-limit checks regardless of this field's
value. Firmware does not need to do anything special to make a QR-originated transaction
"more trusted" — trust comes entirely from the Ed25519 signatures exchanged over BLE, same
as it always has.
